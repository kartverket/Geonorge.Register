## Gaps and open questions

This model was built by reading the repository. Anything below could not be settled from the code
and config alone. Elements and nodes affected carry the **TODO** tag and are drawn with a dashed
border, so the gaps are visible in the diagrams rather than buried here.

### Questions to take to someone who knows

1. **Who calls the synchronisation endpoints, and how often?**
   `api/metadata/synchronize`, `.../inspire-statusregister`, `.../geodatalov-statusregister`,
   `.../mareano-statusregister`, `.../fair-statusregister`, `api/codelist/update-status`,
   `api/metadata/alert-set-status-retired`. The repo proves the endpoints exist and what they do,
   but there is no scheduler in the codebase and no CI/CD configuration committed. Octopus? A
   Windows scheduled task? Something in the monitoring stack? Modelled as **Job scheduler (TODO)**.

2. **Who holds the `register-provider` credentials?**
   `authentication.default.config` has Octopus placeholders `#{RegisterAdminUsername}` /
   `#{RegisterAdminPassword}`, and that role guards `api/alert/add`, `api/{register}/report/save`,
   `api/inspire-statusregister/monitoring-report/save` and `api/codelist/update/kommunereform-2024`.
   Which systems actually authenticate with it? Modelled as **Service monitoring / alert
   publisher (TODO)**.

3. **What are the production IIS rewrite rules?**
   `Web.Dev.config` and `Web.Test.config` define rewrites for `/tjenestevarsler`,
   `register/kartografi`, `register/symbol` and `/api/geolett`. `Web.Release.config` defines none —
   it only strips debug and sets the log level. So production either has these rules configured on
   the server outside source control, or behaves differently from test. Flagged on the production
   IIS node.

4. **Which consumers actually depend on the public API?**
   CORS is `*` and most read endpoints are anonymous, so consumers are unknowable from the code.
   The four in the model (Kartkatalogen, the metadata editor, the report app, monitoring) are the
   ones with hard evidence. PostHog or the access logs would give the real list.

5. **Where do the SMTP, database and Solr hosts actually live per environment?**
   Every real value is injected at deploy time; the repo only has dev defaults. The deployment
   views name the environments correctly but not the machines.

6. **Is there a diagram or model outside this repo that should supersede this one?**
   `Models/Register.cs` carries the header "Generated by Enterprise Architect / Created on:
   24-nov-2014 / Original author: Tor Kjetil". That Sparx EA model is the original source of the
   domain design and is not in this repository. There is also a Backstage entry
   (`catalog-info.yaml`, component `Geonorge.Register`, system `geonorge`) which may carry more.

7. **What is in the risk analysis?**
   `.security/risc/risc-default.risc.yaml` is SOPS/GCP-KMS encrypted and could not be read. It very
   likely already documents some of the trust boundaries drawn here.

### Things the model deliberately does not show

- Internals of the sibling applications (kartografi, symbol, geolett, objektkatalog). They are
  external systems here.
- The full controller and service inventory. 23 controllers and ~45 services are grouped into 16
  components by responsibility; the component descriptions name the files.
- Individual register types as separate elements. They are rows in the same two tables.

### Observations worth a ticket, not a diagram

Noted while reading, listed because an architecture document is where people look for them.

- `Scripts/custom.js` hardcodes `https://kartkatalog.dev.geonorge.no/api/datasets` — a dev host in
  client JS shipped to production, bypassing the `KartkatalogenUrl` setting.
- `Services/SynchronizationService.cs` builds a recursive CTE by string concatenation.
- `Services/FairService.cs` and `Services/Register/RegisterService.cs` make the server fetch
  arbitrary URLs taken from register items — server-side request forgery in shape.
- The `SaveChanges()` fan-out swallows exceptions, so a failed Solr index or audit write is silent.
- Several `HttpClient` instances are created per call inside `using` blocks
  (`DatasetDeliveryService.cs`, `FairDatasetService.cs`), risking socket exhaustion.
- The root `README.md` is truncated mid-sentence, at the step that explains configuration.
